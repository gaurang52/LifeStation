1. Identity & Authentication
Item
	Response
	Amazon Cognito — auth, sign-in, token issuance
	2 — We originally proposed custom JWT auth. Cognito provides the same functionality and reduces implementation effort via managed token issuance, SMS delivery, and session handling. We are aligned.
	API Gateway + Lambda — token validation
	2 — Equivalent to our Express middleware approach. We can adapt.
	AWS Secrets Manager — credential storage
	4 — Small addition. We will absorb.
	Optional SMS MFA via Cognito
	2 — Replaces Twilio-based OTP from our proposal with a native solution.
	Invitation flows — caregiver onboarding
	1 — Already planned.
	Coarse roles in Cognito; fine-grained permissions in middleware
	1 — Fully aligned with our RBAC model.
	Relationship / authorization data store
	3B — We recommend PostgreSQL (RDS). This data is relational (caregiver-subscriber mapping, permissions, constraints), and Postgres provides stronger integrity and query flexibility. DynamoDB remains suitable for key-value use cases (e.g., device tokens, deduplication). Please confirm alignment.
	



2. Data Aggregation
Item
	Response
	API Gateway — client entry point
	2 — Replaces Nginx in our proposal. Fully acceptable.
	AWS Secrets Manager — downstream API credentials
	4 — Small addition. We will absorb.
	Affiliated APIs (account, profile, contact, billing, event history)
	1 — Already planned.
	Device API (GPS, battery, fall signals, location history)
	1 — Already planned.
	Lambda — primary orchestration layer
	3B — We recommend Node.js (Express) on ECS for this layer. Reason: Lambda + Postgres introduces connection scaling constraints (per-invocation connections). ECS allows persistent connection pooling and better stability at scale. Lambda remains appropriate for event-driven workloads (e.g., notifications). Please confirm alignment.
	Caching / lookup support
	3B — We recommend Redis (ElastiCache) alongside Postgres for caching and reducing downstream API load.
